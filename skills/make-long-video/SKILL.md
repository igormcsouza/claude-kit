# make-long-video

## Parameters
Invocation: Claude Code users may use `/make-long-video [topic|auto] [minutes] [velocity=slow|fast]`, `/make-long-video resume[=slug]`, `/make-long-video interview`, or `/make-long-video help`. Codex users may invoke `$make-long-video` with the same arguments or describe the request naturally. In either tool, parse the user's request as these parameters; do not require a slash command.

## Tool compatibility
The workflow, assets, scripts, and video state are shared. Use the current host's native tools for questions, web research, shell/file operations, and delegation; do not assume another host's tool names exist.
- **Claude Code:** use its skill invocation, `AskUserQuestion` when a choice UI is useful, and Agent tool for role subagents. Role briefs are registered globally as agents in `~/.claude/agents/` (see the kit's AGENTS.md), so no per-project copying is needed. Claude Code does not have the Codex ImageGen capability; create original visuals with Manim/vector art or use rights-cleared assets.
- **Codex:** use the skill discovered through `.agents/skills/` (symlink it to the kit's skill dir if the project lacks it), Codex's available user-question mechanism, native subagent/delegation tools, and ImageGen when image creation helps. Read the matching role brief in `~/.claude/agents/video-<role>.md` and include its instructions in the delegated task; the Codex agent does not need Claude's YAML tool/model fields. ImageGen results are saved outside the project by default: copy selected outputs into `videos/<slug>/assets/` and record them in `visual_assets.md`.
- **Either / generic host:** if a preferred tool is unavailable, perform that part directly when practical, or tell the user which capability is unavailable and continue the remaining steps. Never claim a subagent, search, API call, or verification happened unless it did.

| Param | Meaning | Default |
|---|---|---|
| `topic` | Subject of the video, or `auto` to find trending topics | `auto` |
| `minutes` | Target length | `6` |
| `velocity` | `slow` = one subagent at a time, minimal tokens. `fast` = parallel subagents whenever possible, finishes sooner, uses more tokens | `slow` |
| `resume` | List unfinished videos (slug, next step, topic, last update). `resume=<slug>` continues that video from its first pending step with its saved params | - |
| `interview` | Interview the user about how they want their videos and way of working, then save `preferences.json` at the project root (see Interview). Runs nothing else | - |
| `help` | Print this table with the defaults and stop. Run nothing else (no preflight, no subagents) | - |

If args contain `help`, print the table above (and the examples `/make-long-video auto 6 velocity=fast`, `/make-long-video "Docker multi-stage builds" 8`) and end. Unknown `velocity` value: print help and ask. If args contain `resume`: run `python3 ~/.claude/skills/make-long-video/state.py list`, show the result, and if no slug was given ask which to continue using the host's question UI or plain chat. Then load `videos/<slug>/state.json`, reuse its `minutes`/`velocity` (unless the user overrides), run step 0, and jump to the first pending step (`state.py next <slug>`); never redo done steps unless the user asks. If `preferences.json` exists in the project root, read it once at the start of any run, use its `default_minutes`/`default_velocity` when the user gave none, and pass its path to every subagent in the brief; preferences override the skill's tone/voice/visual defaults but never the Legal and safety rules. If it does not exist, mention once that `interview` can create it. Parse params before step 0 and keep them for the whole run.

Output: 1080p MP4, default language Portuguese (pt-BR), default niche = programming, default tone = funny + genuinely useful for work/study; the project's `preferences.json` overrides all three. Use Manim, narration, and whatever visual aids best explain the topic: product/site screenshots, short screen recordings, licensed or user-provided images, original AI-generated illustrations, diagrams, code, and original meme-style graphics. Tools include Manim, an image-generation capability when available, ElevenLabs v4 TTS, ffmpeg, Pillow, and Blender (optional).

## Project-specific config (lives in the project, never in this skill)
Everything that differs per channel/project goes in the project root, not here: `preferences.json` (voice and `voice_id`, mascot, palette, joke bank, CTA, tone, defaults), `video-kit/` (generated by preflight), `videos/` (one folder per video plus `topics.log`), `channel/` (channel assets). This skill and its role agents are global and shared; do not edit them to fit one channel, put it in `preferences.json` instead.

## Interview (`interview` param)
Conversational, not scripted: ask one or two questions at a time in plain chat, using the host's question UI only when it helps; adapt each next question to the previous answer, skip what the answers already settled. Cover, as it flows: channel/audience and goals; tone and humor (what is funny to them, what is off limits); typical length and pacing (calm vs fast voice); subtitles burned in or `.srt` only; voice (pt-BR-AntonioNeural/FranciscaNeural or other), language quirks and slang; visual style, palette, mascot, fonts; topics they love or want to avoid; level of code depth; how involved they want to be (checkpoints, velocity default); music, thumbnails and title style; their own way of doing things and pet peeves. Stop when the picture is clear (usually 8-15 exchanges), then show a 5-line summary and ask for corrections.
Then write `preferences.json` at the project root (merge into the existing file if present; keep unknown keys): flat, human-editable keys such as `channel`, `audience`, `tone`, `humor`, `avoid`, `default_minutes`, `default_velocity`, `voice`, `visual_style`, `palette`, `mascot`, `topics_like`, `topics_avoid`, `code_depth`, `checkpoints`, `pace`, `subtitles`, `music`, `thumbnail_style`, `title_style`, `notes` (free text for anything else). Create or update `CLAUDE.md` for Claude Code and `AGENTS.md` for Codex, each with a short `## Video preferences` section saying: "Read `preferences.json` before any video work; it overrides skill defaults." Do not duplicate preference values. Do this in the main chat itself; no subagents or preflight.

## Token rules (follow always)
- All state lives in files under `videos/<slug>/` (`state.json`, `plan.json`, `narration.md`, `scenes/`, `package/`). Never paste file contents into chat; read only the part needed.
- Main chat is orchestrator only: it talks to the user and delegates all heavy work to subagents (see Orchestration). Trend research: max 4 searches, fetch at most 3 pages.
- Only 2 user checkpoints: (1) pick 1 of 3 topics, (2) review the draft. Everything else runs unattended.
- Scenes are JSON-driven templates (see Kit). Write custom Manim only for 1-2 hero scenes. This is the biggest saving.
- Drafts at `-ql`; final render once at `-qh --fps 30`. Cache per scene (hash of JSON + audio); re-render only changed scenes.
- On errors read only the last 30 lines of the log.
- Review visually with ONE contact-sheet image, not by watching frames one by one.

## Orchestration (subagents)
Role briefs live in `~/.claude/agents/`: `video-researcher`, `video-scriptwriter`, `video-animator`, and `video-producer` (symlinks into the claude-kit repo). Claude Code registers them as native agent types. Codex reads the briefs directly. A project may override a role by adding its own `.claude/agents/video-<role>.md`; project agents win over global ones.
- Main chat orchestrates and delegates heavy research, scripting, audio, and rendering work when the current host supports subagents. Give each delegate only the role brief, slug, relevant file paths, `run_prefix`, and task. Delegates write results to files and report briefly. If native delegation is unavailable, continue directly with the same role brief and keep the user informed.
- **velocity=slow** (default): exactly one subagent running at a time, in pipeline order; scenes are rendered sequentially by a single animator. Cheapest in tokens.
- **velocity=fast**: spawn parallel subagents whenever work is independent, e.g. after the script exists: `video-producer` generates audio while `video-animator` instances render disjoint scene batches (split scene ids, e.g. 3-4 animators); `video-researcher` can start while preflight runs. Never two agents writing the same file. Accept higher token use.
- While subagents run, main chat stays free: answer the user, relay progress in one line, collect feedback. Subagents cannot ask the user; if one returns a question or blocker, main chat asks the user, then continues that delegate using the host's native follow-up mechanism.
- User feedback on a draft: route to the owning role with only the scene ids named. General feedback (voice, pace, sync, mascot, subtitles) also goes into `preferences.json` right away, and `state.py reset <slug> <steps>` sets the affected steps back to pending.
- **Role routing:** In Claude Code, use the registered agent type when available; otherwise delegate a general agent and ask it to read the role brief in `~/.claude/agents/video-<role>.md`. In Codex, use the native subagent facility and include that role brief in the prompt. Keep one continuing delegate per role per video where supported; do not respawn for each fix. In slow mode, only one delegate works at a time.
- **Verify, do not trust.** A report can be missing, interim, or say 'did not view X'. After each report check the files on disk (ls, ffprobe, `qa.md`). If a report names unchecked items, send them to the next role as explicit checks. If two reports disagree, look at ONE frame yourself. Tell the user what was verified and what was not.
- **Rate limit (HTTP 429):** a delegate may stop mid-task. Check what is already on disk (clips, durations) and continue it with the host's native follow-up mechanism; do not redo finished work.
- The main chat cannot hear audio: pronunciation, intonation and music are judged by the user, so offer A/B samples (cents) and say they are unverified.

## Kit (one-time, reused by every video)
In `./video-kit/` (project root, never in `~`): Python env with `manim pillow`. If `uv` is available (check `command -v uv`), use it: `uv venv --python 3.12 && uv pip install manim pillow` in the kit dir, and run every Python tool as `uv run --project ./video-kit <cmd>` (e.g. `manim`, `python`). Without uv, fall back to `python3 -m venv` + pip and call binaries from `./video-kit/.venv/bin/`. System deps manim needs (apt): `ffmpeg libcairo2-dev libpango1.0-dev pkg-config python3-dev build-essential`; install only what is missing. `common.py` provides palette, fonts, subtitle helper, and intro/outro. Scene templates are JSON-driven and should support the visual needed for the story: `code_diff`, `flow`, `reveal`, `terminal`, `chart`, `meme_card`, `hero`, plus still-image/screenshot panels and short screen-recording inserts when a topic benefits from them. Use Manim image objects for stills or ffmpeg composition for video inserts as appropriate; create/reuse a kit helper when it avoids one-off brittle code. Check python3, ffmpeg, manim first; install only what is missing. Use `Text`/`Code`, not `MathTex`, so LaTeX is not required. Blender is optional: render one 5-8s intro once with Eevee/low samples and reuse it forever.
`common.py` has flags such as `SUBTITLES` (burned-in on/off). Kit source is part of the per-scene cache hash, and ANY kit change (layout, fonts, flags) makes every clip stale: re-render all scenes, not only the ones touched (check that each mp4 is newer than the kit). The mascot never covers text; her path is checked across the whole scene, not on one frame.

## Video folder (one per video, resumable)
`videos/<slug>/` (in the current project) holds everything for that video: `state.json`, `plan.json`, `narration.md`, `visual_assets.md`, `assets/`, `scenes/`, drafts, logs, and `package/`. `package/` holds ONLY what the user publishes: `video.mp4` (final), `thumbnail.png`, `subtitles.srt`, `package.md` (3 title options, description with chapters + sources/required visual credits, tags). Everything else stays outside it.
`state.json` tracks steps `preflight, topic, plan, script, voice, draft, review, final, package` (each `pending|done` + timestamp). Manage it only through `python3 ~/.claude/skills/make-long-video/state.py`: `init <slug> <topic> <minutes> <velocity>` once the topic is chosen (slug = kebab-case title), `done <slug> <step> [note]` right after each step finishes (main chat runs it, not subagents), `next <slug>`, `tokens <slug>` (Claude-only token estimate, see Finish), `list`, `reset <slug> <step>...` (works from any subfolder). Mark steps done only when their output files exist. Right after `init`, mark `preflight` and `topic` done.

## Pipeline
0. **Pre-run** (always first): run `~/.claude/skills/make-long-video/preflight.sh`. It checks python3, ffmpeg/ffprobe, cairo/pango dev libs, gcc, python headers, blender (optional), then creates `./video-kit` in the project root (cwd) and installs `manim pillow` (uv project if uv exists, else venv+pip). Idempotent. Exit 1 = system packages missing: show the printed `sudo apt install` command to the user, wait for them to run it, rerun. Exit 2 = Python setup failed: read the last 30 lines, fix, rerun. On `READY`, use the printed `run_prefix` before every `manim`/`python` call.
1. **Trends** (if `auto`, delegate to `video-researcher`): search Hacker News, GitHub Trending, r/programming, dev.to. Skip topics already in `videos/topics.log`. Offer 3 options (title, angle, why it is trending, how easy to animate) and ask the user to choose through the host's question UI or plain chat. Pick the one with a concrete takeaway viewers can use this week.
2. **Plan** (delegate to `video-scriptwriter`) `plan.json`: title, hook, `core_point`, `takeaway`, scenes `[{id, template, narration, on_screen_copy, visual, asset_ids, joke, secs}]`. `narration` is exactly what is spoken; optional `on_screen_copy` may add a concise visual-only gag but must not change the spoken facts or the number being counted. Keep one main point per video, a distinct scene structure, and at least one custom hero scene (see Anti-slop). Choose visuals that make the idea easier to see, including real product/site interfaces or screen recordings when relevant. Verify every claim against a source or by running the code. `plan.json` gets `claims: [{scene, claim, status: verified|attributed|removed, source_urls[]}]`: read each source in full (not the first chunk), cut or attribute ('segundo X') what you cannot validate (paywalled = attributed, never verified), and write `sources.md` (claim -> validating URL). `claims` holds only external factual claims, each with at least one `source_urls` (slop_check FAILs "claims without a source URL"). Opinions (marked as opinion in the narration), local code runs and removed items go in a separate `opinions_and_local_runs` list; the star counts and similar numbers come from an official API (e.g. GitHub API) with the date. On-screen factual numbers/dates come from verified or attributed claims or a checked code run. Internal counts (such as three steps in the explanation) must match the script/demo; never invent numerical facts for a joke. Titles never state an attributed claim as fact.
3. **Script** `narration.md` in pt-BR, conversational, short sentences, ~150 words per minute. Write the hook first. Keep it focused on the video's `core_point` and `takeaway` (see Script clarity below).
4. **Voice** (`video-producer`). The voice (`voice`, `voice_id`) comes from the project's `preferences.json`: if set, skip the A/B and generate directly. If not set, A/B a ~20s excerpt dense with English tech terms (cents) across a few candidate voices and let the user pick by ear, then save the choice to `preferences.json`. Main: ElevenLabs `eleven_v4` with that `voice_id`, `POST https://api.elevenlabs.io/v1/text-to-speech/<voice_id>?output_format=mp3_44100_128` with header `xi-api-key: $ELEVENLABS_API_KEY` and JSON `{"text":..., "model_id":"eleven_v4", "language_code":"pt"}` (no voice_settings; ~$0.08 per 1K chars, ~$0.45 per 6 min; `eleven_v4_turbo` is half price, good for drafts; v4 takes audio tags like `[laughs]`; the key cannot list models or read usage). Default engine because it beat OpenAI by ear. Fallback: OpenAI `gpt-4o-mini-tts` (~$0.11 per 6 min, takes tone `instructions`). No Edge TTS (flat, drifted into Spanish). Keys come from env or `. ~/.profile` in the same shell command; never print them or paste them in chat. Pace is calm: natural speed unless preferences say otherwise (viewers can speed up).
   - **pt-PT accent drift (seen once, ~2:40-3:15 of a 7 min video):** v4 can slide into European Portuguese mid-video, mostly in long scenes (30s+). `language_code: "pt-BR"` is REJECTED by `eleven_v4` (only `"pt"`). Fix that the user approved: Take B = one request per sentence, each with `previous_text`/`next_text` (the first sentence gets the previous scene's last sentence) and a fixed `seed` (1234), then concatenate. Prefer this as the default for every scene to prevent drift. Take C (a Brazilian-accent audio tag prefix) is an alternative, not tested by ear. Suspect odd respellings in `tts_overrides` (e.g. "rídmi" for README) if drift persists. To locate a user-reported timestamp, map it through the cumulative `durations.json` (never guess the scene; the main chat misattributed it once). Retakes go to `voice_samples/` (keep old files in `voice_samples/old/`), the user picks by ear; then replace only those scenes' mp3, `asr/NN.json`, cues and durations, have the animator re-render only those scenes (durations change), then the producer reassembles.
   - One request per scene (or per sentence with context, see above), identical settings each time; cache each scene mp3 by hash of text+voice+model so retakes only pay for changed scenes; trim trailing silence (keep a 0.3s tail).
   - Spell digit strings and acronyms out in the TTS input only (a TTS dropped the last digit of `123456`); keep the original text for screen and subtitles; mapping in `scenes/tts_overrides.json`.
   - Timing: call `.../text-to-speech/<voice_id>/with-timestamps` instead (JSON: `audio_base64` + character-level `alignment`, tested on v4); decode the mp3, save the alignment to `asr/NN.json`, and derive cues from it (drop `[tags]` and `tts_overrides` respellings, map back to original text). No ASR service needed. Pronunciation (dropped digits, odd terms) is checked by ear at draft review; spelling digits out in the TTS input is the guard.
   - Outputs: `scenes/NN.mp3`, `scenes/cues.json` (per scene `[{start,end,text}]` in seconds, original spelling, from the alignment timestamps), `scenes/durations.json` (ffprobe + 0.4s).
   - A joke or punchline with bad intonation: make 2-3 takes (deadpan; resigned; sentence by sentence with fixed pauses) in `voice_samples/`; do not overwrite until the user chooses.
5. **Draft render** (`video-animator` renders, `video-producer` assembles and QAs) at `-ql`, mux each scene with its audio, concat with ffmpeg, add `.srt`. Build the contact sheet (`ffmpeg -vf fps=1/10,scale=320:-1,tile=4x`), check it, check audio/video length match and loudness. Fix issues before showing the user.
   - **Draft QA lessons (the first pass cost 4 render/QA rounds):** (a) loudnorm the draft to about -16 LUFS from the first assembly (first draft came out at -24); check true peak with ebur128 `peak=true`, not sample peak. (b) Build subtitles from the alignment: word-aligned splits, max 2 lines of ~42 chars, no cue over 6s, from the first build (not proportional by characters). (c) Mascot: the animator brief says up front that her path is computed in `common.py` from free zones (clear of every text/panel bbox, re-checked when elements appear, peeks only from a panel's side, never hidden >3s, hops about every 3s); patching scene by scene took 3 rounds. QA with a 3s-interval contact sheet per scene plus full-size mid frames of the busiest scenes. (d) Stamps/chips/labels: verify they sit inside their box and clear of text at full size. (e) Send ALL QA problems to the owner in ONE message, fix at the root (shared kit), and do at most 2 fix rounds before showing the user the draft with the remaining minor items listed; the user's review catches the rest. (f) If any kit file changes after QA, re-render everything (check mp4s are newer than the kit).
   - Sync: the animator schedules every beat from `cues.json`: it starts at or just after (max 0.2s) the cue start, never before, and holds until the cue ends. Long scenes get extra beats and idle motion (no visual over 30s).
   - Name the draft's `.srt` differently from the mp4 (players auto-load a same-name `.srt` and show doubled subtitles).
   - Producer QA checklist, written to `qa.md` (scene ids + problem; visual fixes go back to the animator, then re-QA): run every on-screen code snippet; frames at cue-0.35s and cue+0.9s of the first beats prove no beat is early; mascot sweep every ~3s; text, labels and axes not overlapping; dimmed text legible; loudness about -16 LUFS, true peak <= -1.5 dBTP; no trailing silence; A/V lengths match. Anything not checked is listed as unverified.
6. **Checkpoint 2**: give the user the draft path, a short summary, the minor open items, and what is verified vs unverified (audio is always unverified by the assistant). Ask once whether subtitles are burned in or `.srt` only (the `.srt` always ships). Apply fixes only to the scenes they name. The draft is low-res on purpose (-ql, ~180 kbps); if it looks blocky or corrupted on the user's machine, check with `ffmpeg -v error -i file -f null -` (clean = file is fine) and suggest turning off the player's hardware decoding (VLC: `vlc --avcodec-hw=none file`) before blaming the render.
7. **Final** (`video-animator` then `video-producer`): clips to `scenes/final/NN.mp4` at `-qh --fps 30`, 1080p, H.264 yuv420p CRF 17 (draft bitrate is far too low); the same beats and cues as the approved draft, with a full-size frame check per scene. Assemble `final.mp4` (CRF 17-18, AAC 192k, faststart, about -16 LUFS), no burned-in subtitles unless the user chose them. Mix music only if a royalty-free or synthesized track exists in `./video-kit/music/` (duck about -20 dB under voice) and keep a `final_nomusic.mp4` so the user can choose; otherwise no music. ffprobe and fully decode the result.
8. **Package** (`video-producer`) `videos/<slug>/package/package.md`: 3 title options, description with chapter timestamps (from the real cumulative scene start times in the concatenated file, first at 0:00, YouTube format) and a Fontes section (claim -> validating URL from `sources.md` only; never invent links; paywalled sources marked as attributed), tags, thumbnail 1280x720 (3 words max, high contrast, built with Pillow). Copy the final MP4 to `package/video.mp4`; build `package/subtitles.srt` from `cues.json` with per-scene offsets (max 2 lines of about 42 chars, no cue over about 6s, original spelling); thumbnail goes to `package/thumbnail.png`. Run the Anti-slop gate (`slop_check.py`) and give the user the disclosure recommendation. Append the topic to `videos/topics.log`. The user uploads in YouTube Studio.

## Final and package notes
- Final scenes: all clips newer than the kit, 1920x1080 30fps; scene clips alone are low bitrate (~350 kbps for flat vectors), the assembled `final.mp4` is the CRF 17 encode. Keep `final.mp4` (with the synthesized lofi track at -20 dB under voice, about -16.2 LUFS, -2.2 dBTP) and `final_nomusic.mp4`; `package/video.mp4` is the music version unless the user says otherwise.
- The user approves the draft before stamp or layout tweaks made during final QA: report such post-approval tweaks to the user.
- Chapters in `package.md` come from real cumulative scene starts of the concatenated file; the Fontes section lists only URLs from `sources.md`, attributed items marked `[atribuído]`, plus a one-line pt-BR AI-use note.
- Main-chat checks that paid off: files on disk and ffprobe after every report, mp4 newer than kit, `slop_check.py` run by the main chat itself (the producer's report of its result was not enough to see why it FAILed), `state.py tokens` at the end. Reference cost of a 7 min video: about 176 calls, 17M cache read, 46k output (55 main / 121 subagent).

## Quality rules (retention)
- **Hook = first 30s**: 0-5s grab attention, 5-15s prove the title with a real example, 15-30s show the stakes. No self-introduction, no "subscribe" in the first minute.
- **CTA (default; the project's `preferences.json` `cta` overrides it):** one natural like/subscribe ask tied to the topic (e.g. a joke that reuses the video's own metaphor, placed right after the best payoff, after the first minute, never begging) and one concrete question near the end that invites comments, repeated in the outro and in the description. Put both in `plan.json` (scenes `sub` and `outro`) at the script step so they are not retrofitted.
- Change what is on screen every 5-10s; never hold one visual over 30s.
- A new surprise or open loop every 20-30s; a stronger one about every 60-90s. Put the best moment around two thirds in, not at the end.
- Default length 5-8 min (the 5-10 min range holds viewers best).
- Visual first, text second: show the shape or the bad-vs-good code before explaining it.
- Humor: use playful, harmless wording more often when it fits, with a small laugh or visual gag roughly every 10-20s as a loose guide, not a quota. Keep jokes about code, tools, and developer habits; never target people or groups. Humor should clarify or punctuate the idea, not interrupt it. Rotate `preferences.json` `joke_bank`; do not reuse a gag from the previous video, and use any single running gag at most once per video. Prefer a fresh, topic-specific joke.
- Spoken narration is the source of truth for voice and subtitles. Keep it accurate and natural. `on_screen_copy` may use playful typography, shorthand, exaggeration, or a side comment without being spoken, but must preserve any factual number and meaning. Example: the voice says “são três etapas”; screen copy says “3 etapas” with a small stamp “respira, dev”. The subtitle remains “são três etapas”; do not send the visual gag to TTS or cues.
- Manim: `self.wait()` after every animation, one palette for all scenes, vary entry animations (Write, FadeIn, Create, GrowFromCenter), and use opacity layers (main 1.0, context 0.4, structure 0.15) so attention is directed.
- Show only code that actually runs; run it before it goes on screen.

## Script clarity and visual storytelling
- Before drafting, write one plain-language `core_point` and one concrete `takeaway`. Every scene must support one of them. The viewer should be able to answer “what is this video trying to say?” after the opening minute.
- Keep each scene to one idea. Prefer a direct claim, one concrete example, and the reason it matters or what to do next. Define a technical term once in plain language, then use it consistently. Cut repeated explanations, side quests, and jokes that delay the point. Use short signposts when the subject changes (“o problema”, “o que muda”, “como testar”). Preserve useful detail, but stop explaining once the viewer can understand and apply the takeaway.
- Make the visuals carry explanation, not decoration. The mascot is a recurring host, not the only visual aid. When suitable, use at least two distinct non-mascot modes across a video: original Manim/vector animation, code or terminal, chart, actual product/site screenshot, short screen recording, sourced/licensed image, or original meme-style card. Use a screenshot for a real interface, and a short screen recording when the sequence of clicks or behavior matters. Do not force an asset into a topic that is better explained with a diagram.
- **Choose the visual form per idea.** Do not default scene after scene to a pipeline, checklist, or row of cards. First ask what shape best explains the idea: physical analogy, split comparison, annotated real interface, map, timeline, spatial model, scale/proportion, chart, transformation, short demo, or a deliberately brief list when the information itself is a list. Vary adjacent scenes and avoid repeating a visual grammar without a clear teaching reason. A visual aid must reveal a relationship, change, constraint, or evidence; labels alone are not an explanation. Use real screenshots and screen recordings when they add evidence or show behavior, with focused crops/highlights and attribution.
- **Narration-to-screen timing is exact.** Plan visual beats against `scenes/cues.json`, including the cue text that triggers each change. Show a fact or label only when that fact is being said, remove it when narration moves on, and never preview later information. Start a beat at or just after the relevant cue start; keep it through that cue only when it remains relevant. Review the rendered scene alongside its cue map for lagging or leading visuals.
- **Keep the mascot settled but expressive.** Lip-sync should be clearly visible and responsive to narration. ## Anti-slop (YouTube policy; read before plan and package)
Sources (re-check when in doubt, policies change): Help "Generic or Repetitive Content" in YouTube channel monetization policies (support.google.com/youtube/answer/1311392; renamed 'inauthentic content' 15 Jul 2025), Help "Disclosing use of altered or synthetic content" (support.google.com/youtube/answer/14328491), YouTube blog "How we're helping creators disclose altered or synthetic content" (18 Mar 2024), CEO letter "The Future of YouTube 2026", section "Managing AI slop" (blog.youtube/inside-youtube/the-future-of-youtube-2026/).
What YouTube actually says: AI slop is low-quality, repetitive AI content; YouTube extends its spam and clickbait systems against it but does NOT publish a definition or how it detects it. Monetization (YPP) is where it bites: content that looks template-made or mass-produced, with minimal variation, low educational value, or 'image slideshows, templated storylines, scrolling text with minimal narrative, commentary or educational value', and AI content 'using generic or unoriginal templates' without original insight, is ineligible. Allowed: same intro/outro, recurring characters and series if each video has a distinct storyline, focus or concept; AI as a production tool (scripts, visuals for your own concept). Deepfakes and harmful synthetic media are removed. This pipeline is template-driven and uses synthetic voice, so it is exactly the risk profile; the defense is variation, substance and human direction. Rules:
1. **Distinct video, not a fill-in-the-blank.** Each video has its own concept, scene order and visual metaphors, a custom `hero` scene or two, and a different structure than the last ones. Same kit, intro/outro and mascot are fine; the same skeleton with swapped topic words is not. Use screenshots, recordings, or sourced visuals only when they add topic-specific evidence or clarity; don't add them as decoration. `slop_check.py` compares template order and narration overlap with earlier videos in `videos/`.
2. **Original insight over reporting.** Every video has an `aha` and a takeaway the viewer can act on, plus the creator's own analysis or opinion (marked as opinion). Narration never just reads an article; no slideshow of text; the user's review at checkpoints is the human direction (say so in the summary).
3. **Accuracy is part of quality.** Fabricated facts, quotes, numbers or sources are slop and a trust risk: the claims/`sources.md` rule is mandatory, and an unverified item is cut or attributed, never invented.
4. **No impersonation or realistic fakes.** No cloned or real-person voices, no photoreal fake people, places or events, no fake news footage or logos; the mascot and animation are clearly stylized.
5. **Disclosure.** Required for realistic altered/synthetic content a viewer could mistake for real; not required for scripts, ideas, titles, thumbnails, captions, animation or clearly unrealistic content. A realistic-sounding TTS narrator is a gray area (the docs name voice generation of a realistic person; they do not address a stock narrator). Default: tell the user, recommend setting 'AI use: Yes' in Studio (YouTube says disclosure does not limit audience or monetization) and add a one-line pt-BR note to the description (narração com voz sintética; roteiro e animação produzidos com ferramentas de IA, checados e dirigidos por humano). Never present the voice as a human; the user decides.
6. **Honest metadata.** Title and thumbnail match the content, no fake urgency, no doomsday, no keyword stuffing (about 15 relevant tags), no misleading chapters.
7. **Rights and reuse.** Use original or user-owned visuals, or third-party assets whose license/permission allows the intended use. A publicly viewable meme, screenshot, or clip is not automatically free to reuse. Product/site screenshots may appear when they directly support commentary or explanation; keep them accurate, focused, sourced, and credited as required. Do not copy third-party text, characters, or artwork into original graphics. Use synthesized or licensed music and explain sources in your own words.
8. **Volume.** Volume itself is not the trigger, sameness is: each video needs its own research and variation. If the user wants several videos fast (`fast`, batches), warn that near-identical structure is the risk and run the checker per video.
Gate: before marking `package` done run `python3 ~/.claude/skills/make-long-video/slop_check.py <slug>` and show the user its WARN/FAIL lines and the disclosure decision. A FAIL blocks packaging until fixed. The checker cannot judge originality: the user does.
